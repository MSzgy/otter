# 第一课：摸头之后发生了什么

目标：看懂一次物理输入如何变成反馈，并能自己调整体验。今天用按钮代替真实触摸片。

## 先运行再读代码

启动预演台，点一次“摸摸头”。你会看到：

1. 设备立刻眯眼。
2. 设备向 Mac 上报一次触摸事件。
3. Mac 决定让水獭点头，发送一个动作请求。
4. 设备执行预设动作，表情结束后恢复此前状态。

表情和动作独立计时。眯眼不用等 AI 请求，也不用等串口往返；它应该像按键反馈一样及时。

## 代码走一遍

### 1. 页面按钮是暂时的“传感器”

打开 `app.mjs`，找到：

```js
lab.input("touch")
```

真实硬件到货后，触摸片的输入会在 ESP32 固件中产生。现在这行代码让我们提前测试后续行为。

### 2. 模拟设备处理本地反馈

打开 `src/body.mjs`，找到 `input(kind)`：

- 判断是否正在睡眠。
- 判断距离上次触摸是否超过冷却时间。
- 增加触摸计数。
- 调用 `flash()`，短暂切换成开心表情。

设备本地就能完成这些事，不需要读取记忆、发送网络请求或等待模型。

### 3. 模拟 Mac 决定下一步

打开 `src/lab.mjs`，找到同名的 `input(kind)`：

- 收集模拟设备的处理结果。
- 记录触摸事件。
- 如果仍在连接状态，调用 `perform("nod")`。

这里把表情反馈和后续决策分开。以后 Mac 可以根据勿扰、工作状态等决定是否点头。

### 4. 模拟设备接收点头指令

打开 `src/body.mjs` 的 `receive(command)`：

- 格式和协议版本是否正确？
- 是本次连接的会话吗？
- 已经过期了吗？
- 相同 ID 是否处理过？
- 当前设备有舵机能力吗？正在休息吗？

通过校验后才创建动作。`tick()` 根据时间计算当前姿态，使用平滑插值，动作结束时恢复原来的俯仰姿态。

模拟里的角度不直接作为真实舵机标定值。

## 动手练习

### 练习 A：表情时长和动作时长有什么区别

把开心时长设置为 4 秒，点头时长设置为 1 秒。摸一次头。

预期：头先停止，眼睛仍然眯着，随后才恢复原表情。

### 练习 B：为什么连续触摸需要冷却

快速点两次“摸摸头”，展开通信记录。

预期：第一次正常执行，第二次提示冷却；没有多余的点头排队。

试着在 `src/body.mjs` 把 `this.cooldown = 1200` 改成 `2000`，刷新页面。两次触摸之间需要等更久。观察后改回来，避免影响后续已有测试。

### 练习 C：没有 Mac，什么还能运行

断开模拟连接，再摸头。

预期：眼睛仍然回应，但没有点头请求，也没有离线动作积压。表情结束回到离线待机。

这就是“本地交互”和“上层助手”的边界。

### 练习 D：收到两份指令不应该点两次头

连接模拟设备，点“重复发一次”。在日志中比较两份请求的 `id`。

预期：两份 ID 相同，一条执行，一条被拦截。再点一次这个按钮，会产生新的 ID，因此允许新的一次动作。

### 练习 E：过期和断线

点击“让动作过期”：指令有效期 500 毫秒，模拟送达延迟 1400 毫秒。

预期：设备拒绝它，动作计数不增加。

点击“断线后重连”：主机先安排一个延迟动作，随后断线并清队列、建立新会话。演练还会故意回放一次旧会话指令，确认接收端也能拒绝。

## 自己解释这三个问题

1. 为什么摸头后的眯眼不必等待模型？
2. 为什么重新连接后不能把旧点头指令全部补发？
3. 为什么“更大幅度”不可以直接映射为任意舵机角度？

参考答案：即时反馈应由设备本地完成；旧意图可能已经失效，重连后补发会产生意外动作；真实机构存在碰撞、线缆拉扯和承重限制，必须先标定并限幅。
